# Architecture

This chapter is for people who want to work on System4Dispatch itself. It explains how the code is laid out and how a tap on the screen becomes a frame on the bus.

## The big picture

System4Dispatch is written in Rust. The UI uses [Dioxus](https://dioxuslabs.com) 0.7, which compiles the same components either to WebAssembly for the browser or to a native desktop app that renders in the system's web view. The OpenLCB protocol comes from [rolcb](https://github.com/UncommonModels/rolcb).

```text
System4Dispatch/
├── Cargo.toml            workspace; default member is crates/core
├── crates/
│   ├── core/             s4d-core: layout model, Dispatcher, CDI, node config, Simulator (no UI, no I/O)
│   │   └── src/{layout.rs, dispatcher.rs, cdi.rs, config.rs, sim.rs}
│   └── app/              system4dispatch: the Dioxus app
│       ├── Dioxus.toml
│       ├── assets/       style.css, manifest.webmanifest, icon.svg
│       ├── public/       sw.js (service worker, web only)
│       └── src/
│           ├── main.rs           App root, top bar, 50 ms timer
│           ├── desktop.rs        window manager and dock
│           ├── bus.rs            Bus: owns the Dispatcher and the active link
│           ├── storage.rs        Settings and layout persistence
│           ├── track.rs          SVG track renderer (panel and editor)
│           ├── platform/         mod.rs, web.rs, desktop.rs
│           └── views/            panel, throttle, nodes, editor, settings, help
└── docs/                          this book
```

`rolcb` is a path dependency (`../rolcb`, with `std` and `serde` features), so the two repositories must be checked out side by side. Node configuration needs a rolcb recent enough to leave datagrams to the application when the node's `DATAGRAM` protocol flag is set (older versions reject every datagram addressed to the node).

The guiding rule is that **everything that isn't UI or I/O lives in `crates/core`**, where it can be tested on the host with plain `cargo test`, without a browser, a window or hardware.

## rolcb: a sans-IO protocol stack

rolcb is **sans-IO**: it never touches a socket, a serial port or a clock. An application drives a `rolcb::Node` with three calls:

- `node.receive(&frame, now)` for each CAN frame read from the bus, which returns the decoded message (if any) and queues any automatic replies;
- `node.poll(now)` periodically, or at `node.next_deadline()`, for timers such as the 200 ms alias reservation;
- `node.take_outgoing()` to collect the frames it wants transmitted.

The node handles alias reservation and defence, login, Verify Node ID, Protocol Support, Simple Node Information, and answering Identify Producer/Consumer for its registered events. Datagrams addressed to it are rejected automatically unless the application sets the `DATAGRAM` protocol flag, in which case they are passed up as messages; the dispatcher sets it. Messages are sent with `node.send(Message::…)`. The `rolcb::traction` module encodes traction commands and replies and builds train search events; `rolcb::gridconnect` formats frames as text and has a streaming `Decoder` for incoming bytes.

Because rolcb has no I/O of its own, it runs unchanged in WASM, on tokio, and in tests driven by a fake clock. Its [architecture guide](https://www.uncommonmodels.com/rolcb/) explains the model in more depth.

## crates/core

### `layout.rs`

The layout file format as plain serde structs: `Layout`, `Grid`, `Block`, `Turnout`, `Feedback`, `Element` (`Track` or `Label`) and `Shape`. Besides (de)serialising (`from_json`, `to_json`, and `demo()`, which embeds `crates/core/demo-layout.json`), it provides:

- **geometry**: `Shape::legs()` returns a tile's fixed, normal and reverse segments as pairs of directions (0 = N … 7 = NW, 8 = centre), `Legs::rotated(rot)` turns them, and `dir_offset` maps a direction to a point on the tile;
- **editing helpers**: `put` (one element per cell), `remove_at`, `element_at`, `next_id`, and the editor's selection operations `move_cells`, `remove_cells`, `rotate_cells`, `assign_block`, `place_track`, `set_tile_shape`, `paste`, `remove_block` and `remove_turnout`;
- **links**: `set_link` keeps `linked` symmetric and frees old partners; `linked_partner` tolerates one-sided links;
- **validation**: `validate()` returns the list of `Issue`s the editor shows.

See [Layout file format](layout-format.md) for the user-facing description, and the [JSON Schema](schema/layout-v1.schema.json) (built with the optional `schema` feature).

The full API reference for `s4d-core`, generated by rustdoc, is published at [api/s4d_core](api/s4d_core/index.html). It includes the dispatcher's event-handling table and throttle state diagram, and the `s4d_core::testing` bench used by the tests.

### `dispatcher.rs`

`Dispatcher` is the heart of the app: **one OpenLCB node that tracks the layout's state, throws turnouts and runs throttles**. Like rolcb's `Node`, it is sans-IO. It wraps a `Node` and exposes the same `receive` / `poll` / `take_outgoing` shape, plus `next_deadline`.

- `set_layout` registers the node as a **consumer** of every block and feedback event and a **producer** of every throw event. It builds an index from `EventId` to a list of actions (`Occupied(id)`, `Clear(id)`, `FeedbackNormal(id)`, `CommandReverse(id)`, …), and keeps known state for IDs that still exist.
- `link_up` / `link_down` start and reset the node. `link_state()` is `Offline`, `LoggingIn` or `Online`.
- `poll` runs node timers; the first time the node is permitted after a link-up or layout change, it calls `query_state`, which sends the [startup Identify Producer/Consumer queries](openlcb.md#state-queries-at-startup) and schedules two re-queries, `REQUERY_MS` (3 s) apart, of anything still unknown. The panel's ⟳ button calls `query_state` too. `poll` also times out throttles that are stuck searching (5 s) or assigning (3 s), and runs `config`'s timeouts.
- `receive` turns PCERs, Producer Identified and Consumer Identified into block and turnout state through the index, records PCER events in `recent_events`, and dispatches traction replies to throttles.
- `throw`, `toggle` send turnout commands (including the linked partner) and update the node's producer state.
- `acquire`, `retry`, `set_speed`, `set_function`, `emergency_stop`, `stop_all`, `release` implement the [throttle session](openlcb.md#a-throttle-session). Heartbeat requests from a train are answered with Noop inside `receive`.
- `config` is the node configuration client (see `config.rs` below). `receive` feeds it Verified Node ID, Initialization Complete, SNIP and Protocol Support replies and datagrams; `discover_nodes`, `load_cdi`, `read_config`, `read_config_fields`, `write_config`, `config_update_complete` and `restart_node` queue work for it.
- Public state for the UI: `blocks`, `turnouts`, `throttles`, `traffic` (decoded log for the bus monitor, last 300 lines; messages are only logged while `monitor` is on, link up/down always), `recent_events`, and **`revision`**, a counter bumped whenever anything visible changes.

### `cdi.rs`

The CDI parser. `Cdi::parse` turns a node's CDI XML into `Segment`s, `Group`s and `Field`s, working out every field's memory space and address from the CDI Standard's rules (`origin`, `offset`, sizes, `replication`). Replicated groups are expanded into one group per copy, named from `<repname>` ("Input 1", "Input 2", …). `<acdi/>` adds a "User info" segment for space `0xFB` if the CDI doesn't describe it. `Field::decode` and `Field::encode` convert between memory bytes and the text the form shows, checking `min`, `max` and length.

### `config.rs`

`NodeConfig`, owned by the `Dispatcher` as `config`: the list of nodes on the bus (from Verify Node ID and Initialization Complete, with their SNIP and protocol flags) and a **Memory Configuration** client over datagrams. Requests (read CDI, read, write, update complete, reset) wait in a queue and go out one at a time. Each waits up to 3 s for Datagram Received OK, then for the reply as long as the node's reply-pending flag says (or 3 s). Datagrams rejected with a "try again" code are resent up to 3 times. Reads are split into chunks of at most 64 bytes, and `plan_reads` merges neighbouring fields into as few requests as possible. Replies to its requests are acknowledged; any other datagram addressed to the panel is rejected (`0x1042`, or `0x1041` for Memory Configuration commands). Nodes are discovered once per login, not when the layout changes.

### `sim.rs`

`Simulator` is a pretend layout used for the Simulator connection and for tests. It contains genuine `rolcb::Node`s, so the dispatcher exchanges exactly the same frames with it as it would with real hardware:

- a **layout controller** node that produces every block's occupied and clear events (with correct Valid/Invalid states for Identify Producer), consumes every throw event, and produces feedback events 400 ms after a throw;
- a **command station**: when it sees Identify Producer for a train search event, it creates a new train node for that DCC address (with its own Node ID and alias, logging in like any node), and that node answers. Train nodes accept Assign/Release Controller, Set Speed, Set Function, Emergency Stop, Query Speed/Function and Noop, and send a heartbeat request to their controller every 10 s;
- **random occupancy**: every 3 s it flips a random block and reports it with a PCER;
- **configuration**: the layout controller serves a CDI (`SIM_CDI`) and answers Memory Configuration reads and writes. Its settings (random occupancy on/off, the occupancy period and the feedback delay) take effect at once, and writing its user name in space `0xFB` changes its SNIP.

Since the simulator models a specific layout, `Bus::set_layout` rebuilds it whenever a new layout is applied while it's connected.

### Tests

`cargo test` runs the core tests. The dispatcher tests use a small bench that runs a `Dispatcher` and a `Simulator` against each other on a virtual clock, passing frames back and forth: logging in and learning block state, throwing with and without feedback, linked turnouts, acquiring/driving/releasing a train, heartbeats, link loss, search timeouts, re-querying state that is still unknown after login, and node configuration (discovering nodes and their names, reading the CDI and values and writing them back, errors from nodes without Memory Configuration, silent nodes timing out, and acknowledging incoming datagrams). `cdi.rs` and `config.rs` have unit tests of their own for address computation and request planning. The layout tests cover the demo layout round-trip, rotation, `put` and validation, link symmetry, and lenient parsing.

## crates/app

### The Bus

`bus.rs` defines `Bus`, a cheap `Copy` handle provided as Dioxus context at the app root. It owns:

- the `Dispatcher`;
- the active **link**: `None`, `Sim(Simulator)`, or `Remote` (a function that sends text to a platform transport);
- a `gridconnect::Decoder` for incoming text;
- a `rev` signal that components subscribe to, and a `conn` signal with the connection status (`Disconnected`, `Connecting`, `Connected`, `Error`);
- a **generation** counter, bumped on every connect and disconnect, so a background task belonging to an old connection can tell it is stale and quit, and a **wanted** flag that drives TCP auto-reconnect.

Its main methods:

- `view(|d| …)` reads dispatcher state from a component and subscribes it to `rev`; `peek` reads without subscribing (for event handlers).
- `act(|d, now| …)` mutates the dispatcher (throw, acquire, set speed…) and then **pumps**.
- `tick()` is called every 50 ms by a `use_future` loop in `main.rs`. It polls the dispatcher and the simulator, then pumps.
- `pump()` moves frames until both sides are quiet. With the simulator, frames go straight into `Simulator::receive` and its replies straight back into `Dispatcher::receive`, for up to 32 rounds. With a remote link, outgoing frames are formatted as GridConnect lines and handed to the transport in one write. Afterwards, if the dispatcher's `revision` changed, it bumps `rev`, and Dioxus re-renders the components that read it.
- `connect(settings, auto)` opens the configured link and spawns `run_link`, which waits for `LinkMsg`s from the transport: `Open` (calls `link_up`), `Data` (decodes frames into the dispatcher), `Closed` or `Error` (calls `link_down` and shows the error). For TCP it then waits 3 s and reconnects if the connection is still wanted.

### The platform module

`platform/mod.rs` hides everything that differs between the browser and the desktop. `web.rs` and `desktop.rs` export the **same set of functions**, and Cargo features pick one: `web` (the default) or `desktop`. `desktop` wins if both are enabled.

| Function | Web (`web.rs`) | Desktop (`desktop.rs`) |
|---|---|---|
| `open_serial(port, baud, reuse)` | Web Serial, through a JavaScript snippet run with `document::eval`; `reuse` picks an already-authorised port without a prompt | `tokio-serial` |
| `open_tcp(addr)` | reports "GridConnect TCP needs the desktop app" | `tokio::net::TcpStream` (with `TCP_NODELAY`) |
| `TCP_AVAILABLE` | `false` (the option is hidden) | `true` |
| `serial_ports()`, `serial_supported()` | empty list; checks `navigator.serial` | lists ports; always supported |
| `storage_get` / `storage_set` | `localStorage` | JSON files in the config directory (written atomically via a temp file) |
| `save_file`, `open_file` | download link; hidden file input | native dialogs (`rfd`) |
| `now_ms`, `sleep_ms`, `random_u16` | `Date.now`, `gloo-timers`, `Math.random` | `SystemTime`, `tokio::time`, time and PID |
| `register_service_worker` | registers `sw.js` (https only) | no-op |
| `system_dark`, `set_native_theme` | CSS handles it | asks the desktop portal (`dark-light`), sets the window theme |

A transport is a `Link { tx, rx }`: `tx` accepts `LinkOut::Data(text)` or `LinkOut::Close`, and `rx` delivers `LinkMsg::{Open, Data, Closed, Error}`. On desktop, both serial and TCP share one `pump` task that uses `tokio::select!` to copy bytes in both directions. On the web, the JavaScript snippet talks to Rust through `dioxus.send` / `dioxus.recv`.

`mod.rs` itself has the shared `apply_theme` and `confirm` helpers.

### Views and rendering

- `desktop.rs`: the window manager. `Desktop`, provided as context, holds the open windows (`Win`: kind, position, size, stacking order, minimised and maximised flags) and opens, focuses, minimises, maximises and closes them; closing a throttle window releases its train. `DesktopArea` draws the windows and `Dock` the launchers and the per-window buttons. Dragging and resizing are done by a small page script that moves the window element directly and reports the final geometry when the pointer is released, so the views inside (the panel drawing especially) don't re-render on every pointer move. The script also does the snapping: edges stick to the desktop and other windows, dropping on an edge or corner fills a half or quarter (the size from before is kept in `Win::restore` and handed back to the script in a `data-restore` attribute), and dropping on the top edge maximises. On narrow screens the stylesheet shows only the front window. Window arrangements aren't saved.
- `views/panel.rs` (`PanelView`, plus `MonitorWindow`, which turns bus logging on while it's open), `throttle.rs` (`ThrottleWindow`: one per locomotive, an acquire form until it has a train), `nodes.rs` (`NodesView`, the list of nodes, and `ConfigView`, the Configure window, which renders a node's CDI as a form), `editor.rs`, `settings.rs`, `help.rs`: the contents of each kind of window. They read state with `bus.view` and change it with `bus.act`.
- `track.rs`: `TrackView`, the SVG grid renderer shared by the panel (`Mode::Dispatch`: occupancy colours, clickable turnouts) and the editor (`Mode::Edit`: grid lines, block colours and tags, focus dimming, selection outlines, pointer events for painting and selecting). Segments are drawn as straight lines between opposite directions and quadratic curves through the centre otherwise.
- The editor keeps its unapplied changes in a `Draft` signal provided at the root, so a draft survives closing and reopening the editor window. **Apply & save** calls `save_layout`, which stores the layout and passes it to `Bus::set_layout`.
- `storage.rs`: the `Settings` struct (connection kind, TCP address, serial port, baud, Node ID, options, theme), saved under the key `s4d.settings`, and the applied layout under `s4d.layout`. New installs default to TCP on desktop and serial on the web, with auto-connect off; auto-connect never applies to the simulator. Unknown or unavailable connection kinds fall back to the simulator. `settings_file_json` and `settings_file_from_json` read and write the exported settings file: the settings with the layout under the key `layout`.

## Data flow

```text
                    ┌────────────────────── Dioxus UI (windows) ─────────────────────┐
                    │  Panel  Throttles  Nodes   Editor   Settings (re-render on rev)│
                    └────┬─────────────────────────────────────────────────▲─────────┘
            bus.act(|d| d.throw(..))                                bus.view(|d| ..)
                         │                                                 │
   use_future ──50 ms──► │ bus.tick()                                      │
                         ▼                                                 │
              ┌──────────────────────────── Bus ──────────────────────────┴─┐
              │  Dispatcher (s4d-core) ── wraps ── rolcb::Node               │
              │    receive / poll / take_outgoing        revision ──► rev    │
              │                        pump()                                │
              └───────┬────────────────────────────────────────┬────────────┘
                      │ CanFrames                               │ CanFrames
          Link::Sim   ▼                         Link::Remote    ▼
        ┌──────────────────────┐        gridconnect::format ──► text lines
        │ Simulator (s4d-core) │                    │            ▲
        │  layout controller,  │                    ▼            │ gridconnect::Decoder
        │  command station,    │        ┌─────────── platform ─────────────┐
        │  train nodes:        │        │ web:     Web Serial (JS eval)    │
        │  real rolcb::Nodes   │        │ desktop: tokio serial / TCP      │
        └──────────────────────┘        └───────────────┬──────────────────┘
                                                        │
                                     USB adapter / JMRI hub / Ethernet buffer / rolcb-hub
                                                        │
                                                    LCC bus
```

A tap on a turnout, step by step:

1. `PanelView` handles the click (asking for confirmation if that option is on) and calls `bus.act(|d, _| d.toggle(id))`.
2. `Dispatcher::toggle` works out the new position, and `throw` calls `node.send(Message::Pcer(event))` (twice, for a linked pair) and marks the turnout pending if it has feedback.
3. `act` calls `pump`. The dispatcher's outgoing frames are formatted as `:X195B4…N…;` lines and handed to the link's `tx`.
4. The platform transport writes the text to the serial port or socket.
5. Later, the feedback PCER arrives as text. `run_link` feeds it through the `Decoder` into `Dispatcher::receive`, which clears the pending state and bumps `revision`.
6. `pump` notices the new revision and bumps `rev`. `PanelView` re-renders with the new position.

## How the simulator uses real rolcb nodes

The Simulator connection doesn't fake the dispatcher's view of the world. It fakes the *world*. The simulated layout controller, command station and trains are `rolcb::Node`s with their own Node IDs and aliases: they log in with CID/RID/AMD, answer Identify Producer, send PCERs, and exchange traction commands, all as CAN frames. The Bus passes those frames in memory instead of through GridConnect, but the dispatcher's code path is identical. So anything that works against the simulator exercises the same protocol logic used with real hardware, and the core tests rely on exactly that.
